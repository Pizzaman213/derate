## 1. Executive verdict

**The components are far better than the product.** All 614 collected tests pass (600 fast + network tier, 11 legitimate parametrization skips, 1 deselected slow). The fit calculator, planner, links measurer, resolver, deploy manager, providers service, and UI each individually earn their briefs — the planner flip test passes three independent ways, the fit sweep is monotone and round-trip-clean across 448 checks, and the secret-sentinel sweep found **zero** leaks. But **no code path composes the real implementations together**. The shipped container boots a placeholder page; the only runnable gateway wires all seven ports to stubs; and those stubs actively violate the central claim — the running product will *mint* a fabricated 10.2 GB/s "measurement" on request and will *launch* a 70B model at one million tokens of context because its fit stub is `return fits()`.

**Central claim ("nothing is planned against a spec-sheet number"): TRUE in the libraries, FALSE in every process a user can start.**

### Can this be demoed?

Three different answers:

- **From this working tree, as a UI walkthrough on fixture data — yes.** `python3 -m control_plane.gateway.main` + `cd ui && npm run dev` gives a polished, honestly-labeled ("fixture data") UI with live 1 Hz metrics, verbatim plan reasons, dashed unmeasured edges, and working scenario switching. The real fit/planner can be demoed alongside via `pytest tests/test_planner.py -k flips` and `tests/test_fit.py`. What you cannot demo on this surface: a real refusal through the API (the stub fit never refuses — **C-1**), or a real measurement (the stub fabricates one — **C-1**).
- **From a fresh clone of HEAD — no.** `ui/src/main.tsx`, `ui/src/App.tsx`, and `ui/src/views/NodeDetail.tsx` have never been committed while the tracked `index.html` references them; `npm run build` and the Docker UI stage fail on any clean checkout (**H-6**). The repository has never contained a runnable UI at any commit.
- **As the README's own demo (`docker run` ×2 → cluster forms → plan → refuse → launch) — no.** The container's preferred entrypoint `control_plane.node` does not exist, so it serves a placeholder page while reporting healthy (**C-1**); and even in-library, two nodes started with the same command cannot form a cluster — the joiner is rejected for lacking a token, the path that would surface it as a candidate has no production caller, and the coordinator never browses mDNS (**H-4**).

**Demo-breaking defects:** C-1, H-4, H-5, H-6. Everything else survives a scripted demo.

## 2. Central-claim verdict (evidence)

**Where the claim holds — verified by execution:**

- **The flip (R3, independent of shipped tests):** Llama-3.3-70B on two Sparks, only the measurement mutated: 10.2 GB/s → `PIPELINE pp=2`, reason cites "measured all-reduce is 10.2 GB/s, below the 40 GB/s threshold"; 50.0 GB/s + GDR → `TENSOR tp=2`, reason cites "50.0 GB/s, at or above the 40 GB/s threshold". Decision moves **exactly at** `TP_VIABLE_THRESHOLD` (probe at ±0.1). With `link=None`: conservative plan, rejected list says "no link measurement is available … cannot be justified on an unmeasured path".
- **Constants adjudication (S2, S4 — every literal classified):** `fit/constants.py` and `planner/constants.py` contain zero interconnect numbers — all entries are format facts, physics, or documented config defaults. The only unmeasured constant that shapes a reported bandwidth anywhere is `IB_TO_NCCL_RATIO = 0.42` (record.py:32), which the B brief mandates verbatim and which is disclosed on the record via `estimated=True`, `raw_gbps`, `scale_factor`, and a note. The discrete-GPU bandwidth table (probe.py:41-47) and strength rung 3 (`memory_bandwidth_gbps * gpu_count`) are the spec's own sanctioned ladder, not emitted bandwidth figures.
- **Never emit unmeasured (R5, live):** `/api/topology` unmeasured edges carry `{"measured": false}` and **no** bandwidth field; stale measurements flagged `stale: true`; `cache_hit_pct` is an honest `null`.
- **Fit properties (R2, 448 checks over 4 real shapes × 7 contexts × 5 node counts × 2 seqs):** verdict monotone in context and node count, headroom monotone, every WONT_FIT carries non-empty `limiting_term` + reason, every **non-zero** `max_context_that_fits` round-trips to a fitting verdict (0 failures; 17 return FITS_DEGRADED — loads but slow, disclosed).

**Where the claim breaks — verified by execution:**

- **C-1a:** `POST /api/links/measure {"a":"spark-02","b":"ws-3090"}` against the shipped gateway returned `{"all_reduce_gbps": 10.2, "method": "manual", "measured_at": <now>}` for a pair the topology says was never measured. The API **fabricates a measurement** (gateway/stubs.py:97-108).
- **C-1b:** `POST /api/deployments` for Llama-70B bf16 at **context 1,048,576**, concurrency 16, two Sparks → **HTTP 201, launched**, fit reason "Fits with 24.1 GiB headroom per node" while the same payload reports `max_context_that_fits: 131072`. `StubFit.check` is `return fits() if _HAVE_FIXTURES else None` (gateway/stubs.py:124-125) — and the `None` branch makes the launch guard `if fit is not None and fit.verdict is WONT_FIT` pass vacuously (**H-3**), which is the branch a fixture-less container takes.
